# docs/ - 项目工作文档

本目录保存值得跨会话复用的需求、证据、决策和历史。它不是一条必须逐级通过的流水线，也不要求每次工作都产出文档。

网站访客会看到的正式内容放在 [`../content/`](../content/)；实现细节优先由代码和测试表达。

## 目录地图

| 目录 | 主要角色 |
| --- | --- |
| `user_original_briefs/` | 用户提供的原始阶段性需求 |
| `prd/` | 要解决的问题、目标、范围与验收意图 |
| `research/` | 证据、比较、未知项与建议 |
| `design/` | 体验原则和已采用的设计方向 |
| `specs/` | 值得明确记录的技术契约与取舍 |
| `plans/` | 当前工作的临时组织方式 |
| `iterations/` | 已发生迭代的摘要与复盘 |
| `ideas/` | 尚未承诺的想法 |
| `raw/` | 未加工的来源材料 |
| `archive/` | 不再活跃但仍有历史价值的材料 |

这些分类用于帮助检索，不限制文档之间互相引用，也不要求一项工作必须经过所有目录。

## 协作原则

- **按问题读取**：从根目录 `CLAUDE.md` 开始，只加载与当前任务有关的局部 README 和专题文档。
- **按范围归属**：一个结论由最贴近其主题的活跃文档维护。其他文档链接过去，不复制整段规则。
- **允许变化**：研究可以推翻早期假设，实现反馈可以促使 PRD、设计或 spec 调整，最新用户决定也可以改变既有方向。
- **区分事实与建议**：来源事实、当前决定、候选方案和临时计划应在文字上可区分，避免把建议误读成硬约束。
- **解决冲突**：先看最新用户意图、实际实现、文档适用范围和状态；不能可靠判断时明确记录冲突。
- **适度维护**：只在变化具有跨会话价值时更新文档。不要为保持形式完整而同步无关文件。

## 命名与生命周期

需要时间上下文的正式文档建议使用 `YYYY-MM-DD-<topic>.md`，但可检索性和语义清楚比统一格式更重要。原始资料、用户 brief、固定入口和已有合理命名可以保留原样。

文档可以直接更新，也可以被新文档取代。旧版本只有在能解释决策历史时才需要归档；否则删除重复或无价值内容。必要时在正文中标明草案、采用、暂停或已被取代，无需为所有文件强制同一套元数据。
