- 日期：2026-08-21

- 依据：站点结构 PRD、OriginKit 配额/授权调研、Hero 10 适配评估

## 一、当前判断

用户已明确授权提前保存 Hero 10 源码，这一步已经完成；现在不应该继续消耗额度获取重复组件，也不应该先写大量页面。

接下来仍应先锁定“内容骨架 + 设计母题 + 技术/部署组合”，然后只改造已保存的本地 Hero 10。这样能避免在框架未定、内容未定和响应式未知的情况下继续消耗 OriginKit 配额。

## 二、建议的默认技术方向

以下是建议，不是最终决定：

- 前端与路由：Next.js App Router + TypeScript。
- 样式：Tailwind CSS + CSS 自定义属性承载设计 token。
- 动效：Motion/Framer Motion 作为 React 编排层；简单 hover/颜色变化用 CSS；Canvas 只用于 Pixel Card 等确有需要的效果。
- 内容：作品与早期博客先用仓库内类型化数据/MDX，暂不上 CMS。
- 部署：Vercel 作为第一候选；保留 Netlify、Cloudflare Pages + Workers 作为比较对象。
- 访问计数：Route Handler / serverless function + 持久化 KV/数据库；禁止依赖函数内存或本地文件。

选择这条路线的原因：Hero 10 已面向 Next.js/Tailwind，预览使用 React + Framer Motion；Next.js 可在同一项目内提供站点页面与访问计数 API。官方文档也明确说明静态 export 不提供运行时服务，而 serverless Route Handler 不能依赖跨请求共享内存或可写文件系统，所以计数数据必须单独持久化。
