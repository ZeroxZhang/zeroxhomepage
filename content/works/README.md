# 作品内容

`content/works/` 是作品列表与详情页共享的双语内容源。当前模型为 schema v2；完整加载与校验设计见 [`docs/specs/2026-08-21-portfolio-content-model.md`](../../docs/specs/2026-08-21-portfolio-content-model.md)。

## 文件关系

- `index.yaml` 登记分类和作品 slug。
- `<slug>.md` 保存一个作品的结构化元数据及中英文正文。
- 文件名、frontmatter 中的 `slug` 和注册表条目保持一致。

新增、删除或重命名作品时，应同时处理注册表、关联作品和已有路由。是否需要重定向由当时的发布状态决定，不预设固定方案。

## 当前内容契约

结构化字段供列表、筛选、SEO 和 CTA 使用；正文按以下标记分为两个可独立阅读的语言版本：

```markdown
<!-- locale: zh-CN -->

# 中文标题

中文正文。

<!-- locale: en -->

# English title

English copy.
```

当前关键不变量是：

- `zh-CN` 与 `en` 都提供完整的核心定位、事实、限制和行动入口。
- 中文字段使用默认名称，英文列表字段使用 `_en` 后缀；实际字段以 schema spec 和校验器为准。
- `links[].show_on_homepage: true` 表示在首页作品清单中额外显示该官网入口；每个作品最多一个，且仅用于 `type: website` 的链接。
- `lib/work-slugs.ts` 是部署路由使用的无文件系统清单；测试会强制它与 `index.yaml` 的作品注册表保持一致，避免路由构建追踪无关仓库文件。
- locale 应在 Markdown 渲染前切分，避免把两种正文同时交给页面再隐藏。
- 内容保持框架无关，不嵌入 JSX、组件 import 或样式类。
- 动态事实标注 `facts_as_of`；公开内容不得泄露私密材料、凭证或本机路径。

这些约束用于保障数据完整性。字段、语言或路由模型可以演进，但应作为一次完整契约变更处理，而不是只修改单个文件。

## 编辑方向

详情页首先帮助潜在用户理解作品能解决什么问题、如何使用、是否可信以及下一步是什么。推荐的叙事节奏是：

`承诺 -> 场景 -> 方法或能力 -> 开始方式 -> 证据与边界 -> CTA`

这是写作起点，不是固定模板。不同作品可以调整顺序、标题、篇幅和模块，只要信息清楚、事实可靠，并形成适合该产品的叙事。

`flagship`、`featured`、`standard`、`compact` 表示相对展示深度，不规定硬性字数或章节数量。避免为了满足格式重复卖点。

## 质量判断

- 用户和使用场景优先于开发过程；技术细节只在能解释价值、信任或边界时展开。
- 中文与英文应自然表达同一组关键信息，不要求逐句镜像。
- 不编造经历、评价、数据或市场地位，也不使用无法核验的绝对化宣传。
- 金融、医疗、隐私和私有项目清楚表达适用范围与风险边界。
- 主 CTA 清晰，次要链接不过度争夺注意力。
- 标题层级、链接、关联 slug 和字段一致性最终由内容校验器保障；校验器尚未实现时在评审中人工确认。

研究证据位于 [`docs/research/`](../../docs/research/)。如研究结论、产品定位或前端需求变化，先判断应更新内容、spec 还是两者，而不是把本 README 当作不可改变的上位规则。
